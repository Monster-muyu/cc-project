# 显存计算公式

对应代码：`vram_calc/core/estimator.py`（单机）、`planner.py`（多机复用）、`quant.py`（字节表）、
`engines.py`（引擎开销档案）、`calibration.py`（日志标定）。

> **单位约定**：公式里 GB = 10⁹ 字节（显卡标称口径，24GB 卡 = 24×10⁹）。
> vLLM 日志打印的是 **GiB**（2³⁰），1 GiB ≈ 1.074 GB，对照实测时注意换算。

---

## 1. 总公式（每卡）

```
total_每卡 = W(权重) + KV(缓存) + A(激活) + O(引擎开销)
usable    = 显卡VRAM × 显存利用率 safety_factor（页面滑条，默认 0.9）
headroom  = usable − total
```

各项均按并行方式切分：dense 权重除以 TP×PP，专家权重除以 EP×PP，KV 按层/头切分（见下）。

## 2. 权重 W

```
dense_params = params_b − expert_params_b          # MoE 拆开算
W = ( dense_params×bpp/(TP×PP)  +  expert_params_b×bpp/(EP×PP) ) × (1−cpu_offload)
```

- `bpp` = 每参数字节数，由量化格式决定（`quant.py` QUANT_BYTES）：

| 量化 | bpp | 说明 |
|---|---|---|
| fp16 / bf16 | 2.0 | |
| fp8 | 1.0 | |
| int8 | 1.05 | 含 group-scale 开销 |
| int4 | 0.55 | 含 group 开销 |
| gguf-q4_k_m | 4.5/8 | GGUF 按 bpw/8，q2_k…q8_0 同理 |
| exl2 | bpw/8 | 默认 bpw=4.0 |

- `cpu_offload`：层卸载到 CPU 的比例，GPU 上只留 `(1−cpu_offload)`。
- MoE 时 EP 只对专家部分生效；非 MoE 模型 `ep_eff = 1`，EP 无意义。

## 3. KV 缓存（按"请求负载"口径）

```
kv_layers   = 模型 kv_layers 字段，为 0 时取全部层数
              # GDN/线性注意力混合架构（Qwen3.8/Next 等）只有 full-attention 层持有 KV
KV_每卡 = 2 × (kv_layers/PP) × context_len × (kv_heads/TP) × head_dim × kv_bytes × concurrency
          × (1−cpu_offload) / 10⁹
```

- `2` = K 和 V 两份；`kv_bytes`：fp16/bf16=2，fp8=1（**无 int8**——vLLM/SGLang 的
  `--kv-cache-dtype` 只有 auto / fp8 / fp8_e5m2 / fp8_e4m3）。
- 这是"你要跑的负载需要多少 KV"，**vLLM 实际不按它预分配**——启动时 KV 池直接
  填满利用率余量（真实容量见 §6）。展示它只是让总量随上下文/并发动起来。

## 4. 激活 A（瞬态）

```
A = max_num_batched_tokens × hidden_dim × 2字节 × 12 / 10⁹ / (TP×PP) × (1−cpu_offload)
```

- 按 chunked-prefill 的批 token 数（`--max-num-batched-tokens`，默认 8192）算，**不是**
  context×concurrency——激活是瞬态的，FlashAttention 下很小。
- `12` 是启发式系数（每 token 约十几个激活张量）；计算始终 fp16（2字节），与权重量化无关。

## 5. 引擎开销 O

```
O = baseline_gb + min( 常驻权重GB × weight_ratio, cap_gb )        # 引擎档案
```

| 引擎 | baseline | weight_ratio | cap |
|---|---|---|---|
| vLLM | 1.5 GB | 0.06 | 6.0 GB |
| SGLang | 1.2 | 0.05 | 5.0 |
| llama.cpp | 0.3 | 0.02 | 1.5 |
| Ollama | 0.8 | 0.04 | 3.0 |

系数是占位启发式；**真实日志标定优先**（单机页"日志标定"，存 `~/.vram_calc/calibration.json`）：

```
O_实测 = util × VRAM − W_日志 − KV池_日志
```

日志三行怎么读（V0/V1 通用，`calibration.py`）：

| 日志行 | 取值 |
|---|---|
| `Loading model weights took X GiB` | W_日志 |
| `GPU KV cache size: X MiB` | KV池_日志（÷1024 变 GiB） |
| `# CUDA blocks: N` | 池 token 数 = N × 16（block_size=16） |
| `can hold up to N tokens` | 池 token 数（优先） |

结果为负说明数字对不上（利用率填低了），接口直接 400 拒绝。

## 6. KV 池真实容量与三态判定

```
non_kv       = W + O + A                                  # 每卡固定占用
kv_budget_每卡 = max(usable − non_kv, 0)
kv_pool_全模型 = kv_budget_每卡 × (TP×PP)                  # EP 卡只放专家不放 KV
bpt          = 2 × kv_layers × kv_heads × head_dim × kv_bytes   # 每 token 全模型字节数
max_kv_tokens = kv_pool_全模型 × 10⁹ / bpt
```

判定（对齐 vLLM 语义）：

| verdict | 条件 | 含义 |
|---|---|---|
| **over** | non_kv > usable | 模型装不下，启动即 OOM |
| **ok** | context×concurrency ≤ max_kv_tokens | 装得下且负载进池 |
| **tight** | 装得下但负载超池 | preemption/换页，变慢但不炸 |

并发承载 = ⌊max_kv_tokens / context_len⌋（并发敏感度小图的口径）。

## 7. roofline 解码吞吐（粗估）

```
decode_tps ≈ 0.65 × 显存带宽(GB/s) / 每卡权重GB
```

decode 阶段带宽受限：每生成 1 token 至少把常驻权重读一遍，`0.65` 合并了 KV 读取与低效。
DP 多副本时吞吐 × dp（多机规划页方案卡上的 ≈tok/s）。

## 8. 多机规划怎么用这些公式

四类候选（单机 / DP / 跨机PP / 跨机TP）都是**同一套 estimate() 换并行参数**：

- TP 约束：2 的幂，且整除 attn_heads；MoE 时 ep = tp
- DP：每个副本吃 ⌈concurrency/dp⌉ 的并发，吞吐 × dp
- 跨机 PP：网络建议 ≥25Gbps（万兆起）；跨机 TP：≥100Gbps（IB/RoCE）
- 机器台账里"每卡占用/可用"就是 §1 的 total/usable，同型号 GPU 分组、混插不参与

## 9. 实测对照（2026-08-25 日志：Qwen3.6-27B fp8，2×RTX 3090，TP=2，util 0.85）

| 量 | 本工具公式 | 日志实测 | 差异原因 |
|---|---|---|---|
| 权重/卡 | 27×1.0/2 = **13.5 GB** | `Model loading took 14.46 GiB` ≈ 15.5 GB | 名义 27B vs checkpoint 实际 28.75 GiB（含 embedding 等）；GiB→GB |
| usable/卡 | 24×0.85 = **20.4 GB** | （vLLM 按 0.85 填池，一致） | |
| KV 池/卡 | 20.4 − 15.5 − O ≈ **3~4 GB** | `Available KV cache memory: 4.58 GiB` | 引擎自身 profile 的开销略小于实际 |
| 池容量 | — | `GPU KV cache size: 285,074 tokens` | 反推 bpt ≈ 9.16 GiB×2³⁰/285074 ≈ 34.5 KB/token |
| 启动 | — | **正常启动**（fp8 KV + FLASHINFER） | 印证：Ampere 无 FP8 单元也能跑 fp8，只是软件路径 |

结论：公式骨架与实测同向，误差集中在 (a) 名义参数量 vs checkpoint、(b) 引擎开销系数——
所以有"日志标定"功能：拿一次启动日志把 O 校准成这台机器的真实值。
